# AGENTS.md

Compact guide for OpenCode sessions working in this repo. Read alongside `README.md` and `docs/testing.md`.

## What is Legion

Legion is a **multi-agent collective framework**: one always-on persistent process hosting participants — AI agents (LLM agentic loop), services (code modules), users (human via connector), and mocks (testing) — that communicate by sending messages. Any participant can talk to any other through the same model. It is not a chat app you start and stop; external channels (web, Teams, Slack) connect to a running process simultaneously. Agents run autonomously, services react to events, humans reach in through connectors to direct, approve, or monitor.

Guiding philosophy (see `docs/legion-v2-greenfield-spec.md` for full design):

- **One process, one collective.** No routing/auth/delivery logic branches on participant `type`; type only describes the internal driver.
- **`communicate` tool is the hub.** Sync (blocks until response) or fire-and-forget (with `replyTo` naming a participant). `MessageRouter` replaces any "session" concept.
- **Conversations are branching message trees**, not arrays. Keyed map of messages; active chain reconstructed by walking `parentId` from `activeBranchHead` to root. Supports edit/re-run, prune, compaction — all historical nodes remain recoverable.
- **AuthEngine is a pure predicate** answering `auto` / `requires_approval` / `hidden` (absent). Only tools explicitly listed in a participant's `tools` map are visible to the LLM. Approval bubbles up the call chain emergently to an authorized approver or boundary connector; fails closed if none.
- **Management actions are ordinary authorized tool calls** — no separate permission layer. `create_agent`, `retire_agent`, policy edits are tools gated by the acting participant's `ToolPolicy`.
- **MCP servers are tool sources, not participants.** Declared in workspace config; tools registered as `mcp__<server>__<tool>` in the global `ToolRegistry`.
- **Connectors are channels, not participants.** Boundary connectors map external identities to participants; core knows nothing about identity providers.

## Toolchain

- Node >= 20. npm workspaces, pure ESM (`"type": "module"`, `NodeNext` resolution).
- TypeScript strict + `noUnusedLocals` + `noUnusedParameters` + `verbatimModuleSyntax`. Don't leave unused vars/params; always use `.js` extensions in relative imports (including source `.ts` files).
- Prettier: single quotes, semicolons, trailing commas, 100 cols, 2-space. Run `npm run format` / `npm run format:check`.

## Commands

| Task                               | Command                                        |
| ---------------------------------- | ---------------------------------------------- |
| Install                            | `npm install`                                  |
| Build (all composite pkgs)         | `npm run build` (`tsc --build`)                |
| Clean build cache                  | `npm run clean`                                |
| Typecheck (force rebuild)          | `npm run typecheck`                            |
| Dev server (live reload, no build) | `npm run dev`                                  |
| Production start                   | `npm start` (requires prior `npm run build`)   |
| Unit tests (core/runtime/types)    | `npm test`                                     |
| Watch unit tests                   | `npm run test:watch`                           |
| Coverage                           | `npm run test:coverage`                        |
| Web package tests (happy-dom)      | `npm run test --workspace=packages/web`        |
| E2E (Playwright)                   | `npm run test:e2e`                             |
| Single vitest file                 | `npx vitest run packages/core/src/foo.test.ts` |
| Single vitest test by name         | `npx vitest run -t "test name"`                |
| Single e2e spec                    | `npm run test:e2e -- tests/auth/login.spec.ts` |

Required order before claiming done: `npm run format:check` -> `npm run typecheck` -> `npm test` (and web tests if touching `packages/web`).

## Dev vs production wiring

- `npm run dev` = `tsx watch --tsconfig tsconfig.dev.json ... legion.js --dev`. `tsconfig.dev.json` defines path aliases `@legion-collective/types`, `@legion-collective/core` pointing at `src/index.ts` — no `dist/` needed. Backend reloads on `.ts` change; frontend HMR via Vite middleware mounted in Fastify. Single port (default 3000).
- Production (`npm start`) loads from `dist/` and requires `npm run build` first. `bin/legion.js` switches import path based on `--dev` flag.
- Don't edit `dist/` — generated by `tsc --build`. Don't edit `tsconfig.dev.tsbuildinfo`.

## Package boundaries

- `packages/types` — shared TS types only; no runtime code; coverage reads 0% (expected).
- `packages/core` — engine: runtimes, tools, auth, conversations, services, providers, storage. Depends on `@legion-collective/types`.
- `packages/runtime` — Fastify HTTP + WebSocket entry point. `bin/legion.js` is the process entry. Depends on `@legion-collective/core`.
- `packages/web` — Vue 3 + Vite + Tailwind SPA. Built by `vue-tsc --noEmit && vite build`. Has its own vitest config (happy-dom) — NOT covered by root `vitest.config.ts` (excluded). Build output served by `@fastify/static` in prod.
- `packages/e2e` — Playwright suite; not part of `tsconfig.json` project references.

Import direction: `types` <- `core` <- `runtime`/`web`. Never import runtime/web from core or types.

## Tests

- Vitest globals enabled (no need to import `describe`/`it`/`expect`).
- Test file conventions: `*.test.ts` (unit), `*.integration.test.ts` (integration, skipped by default), under `packages/**/src/**`.
- Integration tests gated by env vars — see `docs/testing.md`:
  - `LEGION_INTEGRATION=1` — starts real Fastify on port 3000; port must be free.
  - `LEGION_MCP_INTEGRATION=1` — spawns real MCP subprocess.
  - `LEGION_OPENAI_INTEGRATION=1` — requires live OpenAI key; model `gpt-4o-mini` (override `OPENAI_MODEL`).
  - `npm run test:coverage:integration` = shorthand for `LEGION_INTEGRATION=1 LEGION_MCP_INTEGRATION=1 vitest run --coverage` (no OpenAI).
- E2E prerequisites: `npm install` + `npm run build` + `npx playwright install chromium`. `global-setup.ts` spawns Legion on port 4000 and a mock OpenAI provider on port 4001 in a temp workspace; uses `LEGION_BOOTSTRAP_PASSWORD=legion-e2e-test`.

## Runtime / workspace

- Workspace root resolved as: `LEGION_WORKSPACE` env > first non-flag CLI arg > `cwd`. Workspace data lives under `.legion/` (conversations, services, credentials, providers, config.json all gitignored).
- Provider API keys belong in `~/.config/legion/config.json` or env vars — **never** in workspace `.legion/config.json` or committed `.env`. (`.env` is gitignored but exists locally.)
- `LEGION_BOOTSTRAP_PASSWORD` sets a deterministic bootstrap operator password (for Docker/scripts/e2e).
- MCP tools registered as `mcp__<server>__<tool>`.
- Process entry: `packages/runtime/bin/legion.js`. Shutdown via SIGINT/SIGTERM.

## Conventions that differ from defaults

- ESM with `.js` import extensions in `.ts` source is mandatory (NodeNext), not optional.
- `verbatimModuleSyntax` requires `import type` for type-only imports.
- Web tests must be run separately from root vitest — root config excludes `packages/web`.
- Integration tests are opt-in via env vars, not opt-out.
- Every collective operation is a tool call over `POST /api/execute` — no CRUD REST endpoints to add.
