A multi-agent collective framework

An always-on process that hosts AI agents, automated services, and human users who communicate by sending messages to each other.

Legion is not a chat app you start and stop. It is a persistent process that external channels connect to simultaneously. Agents run autonomously, services react to events, and humans reach in through connectors (web browser, Teams, Slack) to direct, approve, or monitor. Any participant can talk to any other — a web user logged into the browser UI, an external integration, and an AI agent mid-task all participate through the same model.

01

Design principles

The guiding philosophy of the framework. Each one is enforced in the code, not just stated.

1

One process, one collective

No routing, auth, or delivery logic branches on participant type; type only describes the internal driver.

2

communicate is the hub

Sync calls block until response; fire-and-forget names a replyTo participant. The MessageRouter replaces any "session" concept.

3

Conversations are branching trees, not arrays

Messages link by parentId; the active chain is reconstructed from the head. Edit and re-run, prune, compact — historical nodes remain recoverable.

4

AuthEngine is a pure predicate

It answers auto, requires_approval, or hidden. Approval bubbles up the call chain to an authorized approver or boundary connector; it fails closed if none is found.

5

Management actions are ordinary tool calls

create_agent, retire_agent, and policy edits are tools gated by the acting participant's policy — no separate permission layer.

6

MCP servers are tool sources, not participants

Declared in workspace config; tools register as mcp__<server>__<tool> in the global registry.

7

Connectors are channels, not participants

Boundary connectors map external identities to participants. Core knows nothing about identity providers.

02

Key concepts

Six nouns carry the entire model.

PARTICIPANTS

Agents, services, users, mocks

Each has tool policies and approval-authority profiles. Any participant can talk to any other through the same model.

CONVERSATIONS

Persistent branching threads

Stored as key-value maps with full edit, prune, and compaction history.

COMMUNICATE TOOL

The messaging mechanism

Synchronous calls and fire-and-forget async dispatch via replyTo.

AUTHENGINE

Policy resolution

Tools absent from a participant's tools map are hidden from the LLM entirely. Approval requests bubble up the caller chain or fail closed.

CONNECTORS

Channels to the outside

They bridge participants to external entities (web, Teams, Slack). Authentication is connector-internal.

MCP TOOL SOURCES

External tool registries

Declared in workspace config; tools register namespaced into the global registry.

03

Quick start

Prerequisite: Node.js 20 or later. First launch seeds a workspace, creates a bootstrap operator, and starts the web server.

shell
$ npm install
$ npm run build
$ npm start

# web server on http://127.0.0.1:3000 —
# a random operator password prints to stdout
bootstrap operator password: 9f3a-c2…

ENVIRONMENT VARIABLES

LEGION_WORKSPACEOverride the workspace root directory
LEGION_BOOTSTRAP_PASSWORDSet a deterministic password for the bootstrap operator (Docker / scripted provisioning)
04

Management API

The web connector exposes an authenticated tool-execution gateway — every collective operation is a tool call. No bespoke CRUD endpoints.

RouteDescription
POST /api/auth/loginVerify password, establish session (JWT)
POST /api/executeExecute a named tool as the authenticated participant
GET /wsLive event stream via WebSocket (authenticated)
GET /api/healthProcess liveness check (unauthenticated)
05

Architecture

A TypeScript monorepo — npm workspaces, pure ESM.

types

Shared TypeScript types: tools, conversations, participants, config, events

core

The engine: runtimes, tools, auth, conversations, services, providers, storage

runtime

Process entry point, Fastify HTTP server, WebSocket connector

web

Vue 3 + Vite + Tailwind workspace management console

e2e

Playwright end-to-end tests against a live server

import direction: types ← core ← runtime / web — never the reverse
06

Service SDK

Any npm module can be a Legion service by exporting a LegionService object. Services get scoped storage, a communicate() method, and callTool() with auth enforcement.

my-service.ts
import type { LegionService } from '@legion/core';

export const service: LegionService = {
  async start(ctx) { /* ... */ },
  async stop() { /* ... */ },
  async onMessage(msg, ctx) { /* optional */ },
};
